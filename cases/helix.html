HELIX / 数字员工运行平台

从一份 Agent 能力，
到可部署、可执行、可追溯的数字员工。

01 / 产品问题

能运行一次，与能反复交付，是两套要求。

当 Agent 从个人脚本进入组织使用，使用者需要知道：部署的是哪个版本、在哪台设备执行、使用哪种执行器、凭据是否已配置，以及失败后能否找到原来的任务与产物。HeliX 围绕这些长期运行问题组织产品。

能力需要稳定的交付单元

把员工能力整理为可上传、发布与冻结的版本。任务关联明确的实例和发布版本，让升级与历史执行能够分别追踪。

执行需要明确的控制边界

设备在线、租约、命令、回执和产物分别有状态。平台要处理断连、凭据变化与停止，不能只在界面上显示一个“正在思考”。

按产品职责绘制的架构摘要；执行器支持与本轮真实模型验收分别记录。

六个服务职责

Repository 管员工包和发布；Marketplace 管身份、实例与执行；Gateway 管设备与命令；App Gateway 管控制台实时通道；Feishu Gateway 管飞书；Migration 管共享数据库结构。

CoAgents 如何接入

CoAgents 保留项目、员工、群聊和交付规则，通过适配器提交或继续执行，再把可公开的事件与原件投影回工作群。平台能力可供不同上层应用复用。

03 / 员工生命周期

把发布与激活做成可核对的过程。

  1. 01

    上传与发布

    员工包成为明确的 Release，版本是后续部署和追溯的依据。

  2. 02

    部署与配置

    创建运行实例、配置凭据、选择执行器，并等待设备确认。

  3. 03

    测评与激活

    经过配置与测评检查再激活；模型可调用不直接等于员工可交付。

  4. 04

    执行与维护

    记录命令、事件和产物；凭据轮换、停止与退役也纳入生命周期。

04 / 产品取舍

复用执行能力，同时保留来源和状态。

应用与执行分开

CoAgents 专注协作过程，HeliX 专注实例、设备和执行。代价是需要稳定的适配契约、身份映射与错误恢复，而收益是避免每个业务应用重做设备运行层。

发布、实例和命令分别记录

能力版本、部署状态与一次执行各自有身份。这样才能解释“同一个员工为何在不同轮次产生不同结果”，也为回看历史、升级与退役留下依据。

兼容问题保留在证据中

复现时保留原有权限检查，单独记录 Windows 与 POSIX 的差异。测试失败、跳过和定向复核分别报告，避免为了跑通而削弱约束。

源码交接可重新建立环境

保留独立开发线、固定内部依赖和数据库迁移，补充运行脚本与来源核对。代码快照恢复与完整线上服务恢复分别验收。
