01 / 产品问题

一次输出背后，还有版本、权限和责任。

我将目标使用者设定为需要把重复性知识工作交给 Agent 的团队负责人和执行者。以原型中的例行简报任务为例：选择能力只是开始，使用者还需要知道这次由哪个版本执行、读取了哪些资料，以及产物是否可以使用。

执行之前：明确上下文

从市场选择已发布能力，将固定版本部署为设备上的实例；任务创建时保存对应实例、设备与版本。

执行之后：保留判断

生成交付物后，展示检查快照并等待验收。拒绝、重试和最终接受都留在同一条任务历史中。

02 / 关键决策展开

把“生成完毕”和“接受交付”分成两步。

如果工作流停止时就将任务标记为完成，使用者很难区分“系统已经产出”和“结果已经被接受”。因此，我将人工验收设为独立节点，并让每次重试产生自己的交付记录。

  1. 01 / 待验收

    先看产物与依据

    执行结束后，交付物和本次检查快照一并保存，等待使用者判断。

  2. 02 / 验收不通过

    保留这次判断

    拒绝结果后，原交付、检查快照和验收决定仍可回看。

  3. 03 / 重试

    开始新的尝试

    任务重新排队，保存新一轮交付；需要资料授权时重新请求。

  4. 04 / 接受交付

    由人工确认完成

    新结果通过验收后完成任务，前一次被拒绝的记录继续保留。

选择与代价

多一次验收操作，也需要维护每轮交付的历史。换来的是明确的完成标准，以及比较各次结果的依据。预设 Demo 的重试会重复同样的内容，这条流程验证的是状态和记录保留。

03 / 设计取舍

四项决策，贯穿同一条任务链。

01 / 版本

任务创建时固定版本

可选方案：每次执行都读取实例的最新版本。

选择：任务保留创建时的具体版本，实例升级不会改写历史任务。

代价：维护发布版本与升级限制，让交付来源可以追溯。

02 / 自动化

自动化触发普通任务

可选方案：为自动化单独维护一套运行与结果记录。

选择：触发后复用任务队列、设备约束、授权与验收流程。

代价：自动化也要等待设备与人工决定，异常处理保持一致。

03 / 授权

每次尝试明确访问范围

可选方案：将能力包的权限声明视为已经获得授权。

选择：读取资料前请求允许或拒绝，重试重新授权。

代价：增加等待节点，让访问用途与决定对使用者可见。

04 / 验收

交付与接受分别记录

可选方案：执行结束后直接标为完成。

选择：交付先待验收；被拒绝的结果与新尝试分别保存。

代价：增加人工判断和历史存储，保留结果被接受的依据。

以上为原型设计取舍；目标使用者与价值判断仍需真实使用验证。查看状态实现 ↗
