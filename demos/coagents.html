产品案例 · 设计假设

让 Agent 工作从“能回答”走到“能交付”

问题

当多个 Agent 被复用到不同工作中，仅靠一次对话很难回答：本次任务由哪个版本完成、在哪里运行、是否获准访问资料，以及谁接受了结果。

目标使用者假设

面向需要把重复性知识工作交给 Agent 的团队负责人和执行者：他们需要先选择能力，再把它部署到可见的运行实例，并在每次交付前保留责任和判断记录。

产品方向

以 Agent 市场 → 设备 → 实例 → 任务 → 授权 → 验收 为一条连续工作链，展示能力、运行环境与业务交付之间的关系。

这是产品假设和可执行的静态原型，并非已完成的用户研究或生产效果结论。所有组织、人员、设备、资料和输出均为专门编写的合成样例。

决策 可选方案对比 选择与代价 原型中的验证
版本属于任务上下文 每次运行直接使用 Agent 的最新版本。 创建任务时固定已发布版本，实例升级不改写历史任务。代价是需要维护版本和升级限制，但可追溯交付来源。 状态实现 与 版本冻结测试。
自动化仍创建普通任务 为自动化单独维护运行记录与结果存储。 触发后进入同一任务队列，并保留实例、版本和执行记录。代价是自动化需要遵守任务状态约束，收益是异常、暂停和验收使用同一规则。 自动化状态实现 与 关联任务测试。
能力声明不等于资源授权 将 Agent 的能力或实例配置视为已获得全部资源访问权。 访问合成资料时停在一次明确的允许或拒绝决定；重试时重新请求。代价是多一个等待节点，但不会把用途和范围藏在系统内部。 允许、拒绝与重试历史测试。
完成执行不等于接受交付 模型或工作流停止后直接将任务标记为完成。 将交付、检查快照和人工接受拆成独立状态；拒绝后保留已有证据，再开始新尝试。代价是增加验收动作，但能比较各次交付。 交付历史与证据快照测试。
