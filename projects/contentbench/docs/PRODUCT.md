# 产品设计：营销内容的事实与审核闭环

目标用户：需要跨渠道复用产品事实的小型内容团队。问题假设：同一产品的稿件容易在改写中遗失权益说明、编造数据、覆盖已审核版本。本项目尚未访谈真实团队，不能把假设当作已验证需求。

产品闭环：固定 brief（读者、目标、语气、事实及出处、禁用词、必带说明）→ 单次模型起草 → 确定性规则检查 → 人工修订 → 审核 → 导出快照。采用单次生成工作流，不包装成自主营销 Agent；不做未经授权的渠道发布。

核心取舍：

- 模型输出只生成 draft，不能提供审核状态；Pydantic 禁止额外字段，引用必须来自当前 brief。
- 规则问题允许保存，方便复盘；阻止批准。生成结构无效或错误引用则整次回滚，记录失败事件。
- 提交编辑创建不可变内容的新版本，原批准不继承。审核只能针对最新版本，通过 version 与事务避免竞态覆盖。
- 导出时在同一 SQLite 事务读取所有最新批准版本并保存快照，后续编辑不污染已交付内容。
- 规则明确声明 semantic_verified=false。人工确认必需，但不声称共享令牌等于多角色审签。
- 单服务、SQLite WAL、短事务；模型请求不占用数据库事务，单应用进程锁限制生成并发。多 worker 部署需另做全局限流。

验收指标：可重启保留稿件；错误事实 ID 不落库；未审核/已过期版本不进入新导出；有规则阻断项不能批准；历史快照不被改稿重写。真实模型测试另列 schema / fact ID / 规则问题 / 延迟，不混入接口测试。

下一步：用不同真实 brief 做盲审集；评估更强免费本地模型；引入句子级事实对应、改稿差异高亮和 Markdown 导出；有真实用户后测审核用时与返工率，不预先填收益。
