# SupportOps 产品说明

## 问题与目标用户

假设用户是 2–10 人的 SaaS 客服/IT 支持团队：政策散在文档中，回答后未解决的问题需要人工跟进，缺少能够回查来源的反馈记录。本轮未访谈真实用户；这是待验证的产品假设。

首版目标是缩短“找资料→核对→交给人处理”的操作路径，而不是承诺自动解决率。观察指标是检索命中、反馈、工单状态与答复延迟。未建立真实业务基线前不宣称提升百分比。

## 主要产品取舍

1. 有出处再生成：离线模式返回原文，不按关键词套固定回答；用户可以自己导入未预置过的文档。
2. 回答建议与执行分离：系统不直接退款、不发邮件、不改客户账号；由人核对并用工单记录处理。
3. 无命中与失败可见：模型出错时保留检索结果、记录失败类型；无证据时建议补资料或转人工。
4. 历史可复盘：引用在回答产生时冻结；删文档不改写过去答复。运行记录可导出。
5. 状态受后端约束：未认领不能直接完成；解决必须填写处理人和处理记录；过期页面保存收到冲突。
6. 模型可替换：有免费凭据再接模型；没有凭据仍能使用知识检索与工单系统。

## 数据与接口

`documents → runs → feedback / tickets → events`。runs 保存 question、answer、mode、citations、trace、elapsed_ms、usage；tickets 对 run_id 唯一以防重复升级；事件与状态更新同一事务提交。

后端提供 `/api/documents`、`/api/ask`、`/api/runs`、`/api/tickets`、`/api/badcases`、`/api/metrics`。主界面与 API 同源。

## 验收方式

- 导入一篇自己的资料，查询其中事实，查看真实来源片段。
- 查询未知主题不生成无依据回答。
- 对客检索不召回 internal 文档；这是范围过滤，不是角色授权。
- 对回答提交负反馈后可在复盘列表查到。
- 同一回答重复建工单得到原工单。
- 状态跳转错误、缺处理人/解决记录、并发过期版本均被后端拒绝。
- 模型 mock 成功与错误分开验证；后续补充免费真实模型运行报告与对抗性样本。

## 下一版本

优先补真实用户试用与检索失败样本、可修改工单分类/优先级、资料版本更新、评测集导入。随后根据验证需要考虑混合检索、多轮上下文和工单 SLA。真正的角色权限、租户与数据保留策略需要在真实外部团队使用前补齐。
